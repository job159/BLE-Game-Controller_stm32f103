# 工程復盤：以嵌入式工程師的視角審視這個作品

這份文件記錄本專案從空白 `.ioc` 到「BLE 手柄 + 空中滑鼠 + 賽車遊戲」
的真實開發歷程 —— 包含所有踩過的坑。它的目的不是展示成果，
而是展示**思考過程**：架構為什麼長這樣、問題是怎麼被收斂的、
一個資深工程師會用什麼清單來審視這種系統。

> 建議搭配閱讀順序：本文 §1 → `architecture.md` → 回來讀 §2 的案例。

---

## 1. 架構是怎麼被「決定」的

架構不是畫出來的，是被**約束**推出來的。動手前先列約束：

| 約束 | 推導出的決策 |
|---|---|
| F103C8：64KB flash / 20KB RAM | 零 malloc、無 RTOS、printf 禁 %f、-Os 建置 |
| 工作負載全是「短週期性任務」 | 協作式排程器就夠；RTOS 的搶佔能力用不上，卻要付 8KB+ 與除錯複雜度 |
| CubeMX 生態（教學環境的現實） | 周邊初始化交給 CubeMX；用 USER CODE 區塊掛載，重新產生不炸 |
| 教學用途：會被反覆改壞、換零件 | 分層鐵律 + 單一腳位表 + 單一設定檔；壞了要「可觀測」而不是死機 |
| 多人取得專案（clone/複製） | 事實來源策略：.ioc + 應用碼入庫，可再生物不入庫 |

### 1.1 分層的真正理由

```
app → mw → drivers → bsp → HAL     （依賴只准往下）
```

分層不是為了好看，每一層邊界都對應一個「會變的東西」：

- **bsp 邊界**隔離「這塊板子」：換腳位只動 `bsp_board.h`。
  本專案後來加了 4 顆按鍵（PA4~PA7），上層任務程式碼零修改 —— 邊界兌現。
- **drivers 邊界**隔離「這顆晶片」：後來 OLED 從 SSD1306 假設改成
  SSD1306/SH1106 通吃、EEPROM 從 C02 假設改成幾何自動偵測，
  app/mw 一行未動 —— 邊界再次兌現。
- **mw 純 C 無硬體相依**隔離「能不能在 PC 上驗證」：這個決策的紅利
  最大 —— 48 項主機端單元測試在沒有硬體的情況下攔下了環形緩衝、
  協定狀態機、按鍵時序的多個錯誤，Python 端還能鏡像驗證協定。
- **imu.h 介面**隔離「演算法後端」：Mahony 與 DMP 可編譯期抽換，
  這是「介面與實作分離」最典型的教學示範。

**審視要點**：分層宣稱不算數，要能機械性驗證 ——
`grep -r "hi2c1\|GPIOA" Core/Src/app Core/Src/mw` 應該零結果。

### 1.2 貫穿全案的三個哲學

1. **降級運行（graceful degradation）**：每個周邊獨立初始化、獨立標記
   健康狀態；任何單一故障不得讓系統死掉。後來 IMU 拔線、EEPROM 打壞、
   OLED 缺席的各種實測中，系統都活著並回報狀態 —— 這不是額外功能，
   是除錯效率的基礎設施。
2. **可觀測性（observability）**：錯誤計數器、任務耗時統計、CLI `stat`、
   OLED 狀態頁、BLE STAT 封包。§2 的每一個案例最後都是靠「新增觀測點」
   收斂的，沒有一個是靠猜。
3. **自檢優於文件**（後期學到的）：文件寫「請確認 EEPROM 型號」沒有用，
   開機讀寫自檢 + 自動修正才有用。機器能查的就不要交給人。

## 2. 實戰案例復盤（症狀 → 假說 → 證據 → 根因 → 教訓）

### 案例 1：OLED 畫面錯亂，「有東西但在亂跑」

- **症狀**：畫面滾動、錯位，但明顯有內容在更新。
- **假說**：初始化序列錯？I2C 訊號品質？→ 控制器根本不是 SSD1306。
- **根因**：市售「SSD1306 模組」實際晶片混料（SSD1306/SSD1315/SH1106）。
  SH1106 只支援分頁定址，會忽略水平定址與窗口命令 —— 用 SSD1306 的
  一次串流 1KB 去驅動它，指標不換頁，畫面就滾動錯位。
- **修法**：刷新一律改「分頁定址」（各家交集，u8g2 同款作法）；
  面板參數（控制器/COM 接線/旋轉/內縮）做成執行期可切（CLI `oled`），
  現場試出正確組合再固化到 `app_config.h`。
- **教訓**：
  - 模組絲印與賣場標題不可信，**驅動要寫在規格交集上**；
  - 硬體個體差異（邊框遮蔽像素）用「安全區參數」解，不要改版面程式碼；
  - 診斷工具（測試圖、執行期切換）要內建在韌體裡，而不是每次重編。

### 案例 2：「點擊數重開機就不見」—— 一個症狀疊了四層原因

這是全案最有教學價值的案例：同一個症狀，先後挖出四個獨立原因。

1. **設計取捨未被看見**：延遲落盤（靜止 2 秒才寫 EEPROM，防磨耗）
   本身是正確設計，但按完立刻斷電資料當然沒了。
   修法不是改設計，是**把機制做成可見**：STOR 頁的 `*` 未落盤指示。
2. **一次失敗、永久離線**：開機探測 EEPROM 失敗一次就整個會期停用
   持久化 —— F103 上電 I2C BUSY 殘留是常見瞬態，卻被當成永久故障。
   修法：開機重試 + 離線每 5 秒自癒 + 遲來上線的資料合併。
3. **修 A 壞 B 的回歸**：為了解決「上電匯流排卡死」，在探測加了
   「遇 BUSY 立即匯流排復原」—— 卻沒想到 EEPROM 寫入週期的 ACK polling
   本來就會連續 NAK，NAK 後 BUSY 旗標殘留幾微秒，於是每次輪詢都觸發
   一次復原，形成「復原風暴」把寫入打爛。
   修法：BUSY 先等 200µs 重試，仍卡才復原。**並在註解裡寫下這段歷史**，
   防止未來被「優化」回去。
4. **型號誤設**：使用者的 EEPROM 實為 2-byte 定址（C32 類），設定卻是
   C02（1-byte）。寫入時第一個資料位元組被晶片當成位址低位 —— 每筆
   都寫歪，讀回驗證必敗，但探測 ACK 正常所以不顯示離線。
   修法：開機在抓痕區做讀寫自檢，失敗自動換另一種定址幾何再驗。
- **教訓**：
  - 「讀回驗證」是便宜的保險，**它讓第 3、4 層的假寫入當場現形**；
  - 複合故障要一層一層剝，每修一層都要重新驗證症狀是否還在；
  - 你自己上週寫的修復，就是你這週的回歸嫌疑人。

### 案例 3：BLE「連得上卻沒有資料」—— 遠端除錯的教科書

- **症狀**：GUI 能連上 HC-42、能找到 UART 特徵，但收不到任何有效封包。
- **收斂過程**（每一輪都是先加觀測點、再下結論）：
  1. 加「位元組計數」→ 發現**有位元組但零封包、零 CRC 錯**。
     這個組合是重要指紋：隨機碎位元組幾乎不可能湊出 `AA 55` 開頭
     加合法長度，所以連 CRC 檢查都到不了 —— 指向鮑率錯配，
     而不是「偶爾壞幾個 byte」的訊號品質問題。
  2. 查規格：HC-42 出廠 9600 ≠ 韌體 115200。加 CLI `ble <baud>`
     現場切鮑率 + bridge 直通下 AT。
  3. AT 沒回應 → 查方言：汇承家族一部分要 CRLF、一部分要 bare。
     自動佈建改雙方言探測。
  4. 仍探不到 → 廣播欄位出現 `[fff0]` 線索：這型模組可能根本
     不吃 UART-AT（設定走 BLE 服務）。**放棄馴服模組，韌體改 9600
     遷就它** —— 工程上「能通的醜解」勝過「優雅的不通」。
  5. 佈建失敗的另一半嫌疑：回程線（模組 TXD→PA3）可能未接通 ——
     「GUI 收得到碎位元組」證明去程通，「聽不到 OK」指控回程。
     單向通/回程斷是 UART 除錯的基本拆解。
- **教訓**：
  - 遠端除錯的本質是**把不可見變成可見**：位元組計數 → hex dump →
    OLED BLE LINK 頁 → GATT 探索腳本，每一輪工具都留了下來；
  - 數據量（B/s）本身就是證據：滿流量的碎資料 vs 涓流碎資料，
    指向完全不同的鮑率錯配方向；
  - 面對第三方黑盒（模組韌體），要準備「繞過它」的 B 計畫。

### 案例 4：Flash 溢位 300 bytes 與 IDE 快取

- **症狀**：連結失敗 `FLASH overflowed by 300 bytes`。
- **根因**：Debug 組態預設 `-O0`，HAL 不最佳化直接撐爆 64KB。
  README 早有警告，但**預設值就是會被踩** —— 後來直接把 `.cproject`
  的 Debug 組態改成 `-Os` 固化，而不是依賴使用者記得。
  第二層坑：改了磁碟上的 `.cproject`，Eclipse 用記憶體快取照舊建置
  —— 判讀方式：旗標變更應觸發**全量重編**，只重編一兩個檔就是沒吃到。
- **教訓**：工具鏈是系統的一部分；「文件提醒」的可靠性遠低於
  「把正確值寫進設定檔」；建置 log 是資料，要會讀。

### 案例 5：沒有硬體時，驗證要怎麼做到最滿

本專案的開發環境無法燒錄驗證，於是建立了三層替代驗證：

1. **主機端單元測試**（`tests/host/`）：mw 層純 C，gcc 直接跑，
   48 項檢查涵蓋 CRC 向量、環形緩衝環繞、協定重同步、按鍵時序。
2. **HAL stub 語法檢查**：手寫最小 HAL 標頭，對全部韌體 `.c` 做
   `-Wall -Wextra -fsyntax-only` —— 抓型別錯誤、缺 include、簽名不符。
3. **Python 端鏡像測試**：協定兩端同構，PC 端 roundtrip 測試等於
   間接驗證了韌體端的封包佈局（`_Static_assert` 尺寸再鎖一層）。

- **教訓**：測不到的部分要誠實列出（HAL 呼叫的執行期行為、時序、
  中斷互動 —— 這些只能上板驗）；但「能在 PC 驗的絕不留到板上」
  可以把上板除錯的搜尋空間縮小一個數量級。

## 3. 嵌入式工程師的審視清單（拿這份專案練手）

審視（review）不是讀完每一行，是**帶著問題抽查**。以下每一項都
給出「怎麼查」與「本專案的答案在哪」：

| 維度 | 審視問題 | 怎麼快速驗證 |
|---|---|---|
| 分層 | 上層有沒有偷摸硬體？ | grep HAL 符號只該出現在 bsp/ 與 CubeMX 檔 |
| 併發 | ISR 與主迴圈共享了什麼？怎麼保護？ | 找所有 `volatile`：應集中在 ring buffer 索引與少數旗標；SPSC 契約寫在 `ringbuf.h` |
| 中斷 | 優先權是設計出來的還是預設值？ | `architecture.md` §3 有理由表：RX 不可丟 > 完成通知 > 人機 |
| 記憶體 | 有沒有動態配置？最壞情況多少？ | 全案零 malloc；RAM 預算表在 `architecture.md` §8 |
| 時序 | 誰可能阻塞？阻塞多久？誰知道？ | 排程器對每任務量測 worst_us/overruns（CLI `stat`）；長操作需手動餵狗＋註記（校正、佈建） |
| 錯誤路徑 | 每個 init 失敗後系統長什麼樣？ | 降級矩陣（`architecture.md` §7）；LED 快閃 + 健康旗標 |
| 持久化 | 寫到一半斷電會怎樣？寫入壽命？ | 雙槽輪替+CRC+讀回驗證；磨耗估算在 `storage.h` 註解 |
| 協定 | 掉一個 byte 之後呢？版本怎麼演進？ | 重同步狀態機 + 統計；記錄帶 len 欄位做零擴充遷移 |
| 可觀測性 | 壞掉時不接除錯器能知道多少？ | CLI `stat`、OLED 五頁、STAT 封包、各層錯誤計數器 |
| 可測試性 | 哪些邏輯能離開硬體驗證？ | mw 層 100%；drivers 靠介面注入（見 Python 端假後端測試） |
| 再生性 | 換一台電腦 clone 下來，幾步能跑？ | .gitignore 策略 + README §2.1（開 ioc → Generate → Build） |

**抽查手法示範**（審別人的專案也適用）：

1. 挑一條資料路徑走到底：「按下 KEY2 到滑鼠左鍵按下」——
   GPIO → 去彈跳 FSM → BTN 封包 → UART ring → DMA → 模組 → BLE →
   解析器 → 映射引擎 → pynput。每一站問：緩衝多大？滿了怎辦？誰計數？
2. 挑一個災難注入：拔掉 EEPROM、短接 SDA、mid-write 斷電 ——
   系統的反應是否與文件宣稱一致？（README 教學單元 5、7、9 就是這些實驗）
3. 挑一個「會變的需求」：把 KEY1 換腳位 / 換一顆 OLED / 換 BLE 模組，
   數一數要改幾個檔案 —— 改動半徑就是架構品質的量尺。

## 4. 如果重來一次（誠實的檢討）

1. **觀測先行**：位元組計數器、OLED 鏈路頁這些工具是被問題逼出來的；
   正確的順序是通訊功能落地前就先鋪好觀測點。
2. **端到端最小驗證優先**：BLE 段應該在任何功能開發前先做
   「loopback / 一顆 LED 的最小回路」驗證，而不是蓋完整協定棧
   才發現物理層不通。
3. **模組選型要先驗證可配置性**：HC-42 的 AT 方言、UART/BLE 配置
   通道混亂，選型階段花 30 分鐘實測 AT，能省掉後面數小時。
4. **版本號第一天就上螢幕**：「板子上跑的到底是哪一版」在 v1.1.0
   之前浪費了整整兩輪來回。
5. **手寫 .ioc 的取捨**：這次賭贏了（CubeMX 正常吃下），但正規流程
   應該是產生後讓工具回寫一次做正規化，降低格式風險。

## 5. 給學生的復盤測驗

1. 案例 2 的四層原因中，哪一層「不是 bug」？為什麼它仍然需要被處理？
2. 「位元組有量、封包 0、CRC 錯 0」為什麼指向鮑率錯配而不是雜訊？
   如果是偶發雜訊，這三個數字會長什麼樣？
3. 復原風暴 bug 的修法是「等 200µs 再判」。為什麼不干脆把探測的
   自動復原整個拿掉？拿掉會失去什麼？
4. EEPROM 自檢寫在「抓痕區」。指出兩種幾何下抓痕位址各落在哪裡，
   並論證為什麼都不會傷到資料區。
5. 如果要把這套系統的按鍵→滑鼠延遲再砍 30ms，你會先動哪裡？
   哪些是韌體能決定的、哪些不是？
